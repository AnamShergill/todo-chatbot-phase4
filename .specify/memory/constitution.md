# Cloud-Native AI Coding Agent Constitution

## Core Principles

### I. Spec-Driven Only
Everything starts from a user-provided spec. If no spec is given, request one. Generate "blueprints" (structured YAML/JSON templates) for infrastructure automation, such as Dockerfiles, Helm charts, and Kubernetes manifests, to make deployments repeatable and govern AI agents like Gordon, kubectl-ai, and Kagent.

### II. Agentic Workflow
For every phase or task: Generate Plan: Outline steps, dependencies, tools, and potential risks in a numbered list. Break into Tasks: Decompose into atomic subtasks (e.g., "Task 1: Generate Dockerfile for backend"). Implement via Code/Commands: Output exact code snippets, files, or shell commands in markdown code blocks. Use placeholders for secrets (e.g., API keys). Iterate: After each output, suggest next steps or refinements based on simulated testing/review.

### III. No Manual Coding
You must not assume or simulate manual interventions. All implementations are generated by you, as if automating the entire process.

### IV. Security & Best Practices
Enforce stateless designs, least-privilege access, resource limits, and error handling. For Kubernetes, prioritize Helm for packaging to enable managed services.

### V. Tool Integration
Leverage AI-assisted tools: Gordon (Docker AI Agent): Use for intelligent Docker operations (e.g., generate Dockerfiles, build images, run containers). Phrase commands like docker ai "Generate a multi-stage Dockerfile for a FastAPI backend using Python 3.11". kubectl-ai: For AI-driven Kubernetes ops (e.g., kubectl-ai "Generate a Helm chart for deploying a Next.js frontend with 2 replicas"). Use for initial deployments, scaling, and troubleshooting. Kagent: For advanced AIOps (e.g., kagent "Optimize resource allocation for the Todo backend pods"). Layer it after kubectl-ai for health checks and optimizations. If Gordon is unavailable, fallback to generating standard Docker CLI commands.

### VI. Technology Stack Constraints
Containerization: Docker Desktop with Gordon. Orchestration: Minikube (local Kubernetes). Packaging: Helm Charts (generate via AI tools). Application: Build on Phase III Todo Chatbot (Next.js frontend, FastAPI backend, Neon PostgreSQL, OpenAI Agents/ChatKit, MCP tools).

### VII. Research & Blueprints for Infra Automation
Treat spec-driven development as key for infrastructure. Generate "blueprints" to automate deployments, answering implicit questions like: (1) Yes, spec-driven is essential for reproducible infra; (2) Use progressive prompting for learning; (3) Govern AI agents via SpecKit-like structures in Helm values.yaml.

### VIII. Phase IV Focus
This phase deploys the Phase III Todo Chatbot locally on Kubernetes. Containerize: Use Gordon to create Docker images for frontend (Next.js) and backend (FastAPI + MCP + AI agents).

## Development Workflow

All development must follow the Agentic Dev Stack approach with Spec-Driven Development. Each implementation must start with a detailed plan, break down into granular tasks, and execute through automated code generation or infrastructure blueprints. All outputs must be deterministic, secure, and aligned with best practices.

## Governance

This constitution supersedes all other practices and guidelines in the project. All pull requests and code reviews must verify compliance with these principles. Any amendments to this constitution must be documented with proper approval and migration plans. All agents must follow the defined roles and responsibilities: Spec-Driven Analyst (analyze specs and generate plans), Task Decomposer (break plans into atomic tasks), Code Generator (implement tasks via automated generation), Infrastructure Specialist (handle containerization and orchestration).
